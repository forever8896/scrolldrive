Frameline

Frameline makes websites that play like a film as you scroll. You describe what you want; a team of agents plans the shots, generates them, films the camera moves between them, writes the words and lays them out. You approve before anything is paid for, then edit any word or position on the finished site.

The agent pays for its own generation. It holds a wallet whose key it never sees: 1Claw keeps the key in an HSM and signs only payments that fit rules a human set. Every LLM call goes through 1Claw Shroud, and the API key for the LLM provider lives in a 1Claw vault, not in this code.

InputA pitch in plain words, plus up to 6 images
OutputA static site (zip) with a scroll-scrubbed film, ready for any host
Typical cost to the agent$1.44 for a 3-move film at 768p
Typical timeAbout 1 to 3 minutes of rendering

The flow

The studio at /studio shows one step at a time. Two steps spend money, and each needs an explicit approval.

  1. Pitch. One free-form description, optionally with images (your product, your work, your face, a mood).
  2. Questions. The producer infers everything it can and asks only what is missing and would change the film, one question at a time with tap-to-answer options. A rich pitch gets no questions.
  3. Brief. The understood brief, editable in place, with controls: kind of site, look, length (2 to 6 camera moves) and quality (768p or 1080p). The price updates live.
  4. Storyboard. The art director writes every keyframe and camera move, picks the colours and font. Nothing is generated yet.
  5. Keyframes approval 1. The stills are generated. Any one can be redone with an edited prompt.
  6. Film approval 2. Each camera move is filmed from one still exactly onto the next. Meanwhile the copywriter writes the words and the typographer lays them out on the stills.
  7. Deliver. A live preview of the finished site. Click any text to edit it, change the layout per line, ask the agents to rewrite or re-lay out, then download the zip.

The agents

Each role is a separate, focused LLM call with its own prompt. Their output is always treated as data and validated by code: code, not the model, bounds the number of shots, the price and every field.

RoleModelWhenSeesProduces
ProducerMiMo v2.6 FlashAfter the pitchPitch, imagesBrief, only the missing questions
Art directorMiMo v2.6 FlashStoryboardBrief, images, controlsKeyframe prompts, how each is made, camera moves, theme, font
CopywriterKimi K2When the film is approvedBrief, what each shot showsTitle, tagline, one line per shot, sections, button
TypographerMiMo v2.6 FlashWhile the film rendersEvery still and its lineStyle, title position, per-line position, size and entrance

All four are routed by 1Claw Shroud to OpenRouter. The copywriter writes after the stills exist so it knows what is on screen; it is told never to describe the image or the making of the site. The typographer looks at each still and places text in empty space so it never covers the subject.

Briefs, images and earlier copy are untrusted input. Every prompt says so, model output is parsed as JSON and validated, and Shroud inspects the traffic.

How it uses 1Claw

1Claw is the agent's identity, its keychain, its LLM gateway and its wallet. The studio holds no private key and no LLM API key.

Agent identity

The studio is a 1Claw agent, studio. Its API key is exchanged at POST /v1/auth/agent-token for a short-lived JWT, which authenticates everything below. On a 1Claw runtime the platform injects and renews that token itself.

Vault

The OpenRouter API key is a secret in a 1Claw vault at providers/openrouter/api-key. Shroud fetches it server-side; the app never reads it.

Shroud

All LLM calls go to shroud.1claw.co with the agent's JWT and X-Shroud-Provider: openrouter. Shroud injects the provider key from the vault and screens prompts and responses. On the Pro plan this needs no 1Claw credits.

Wallet and signing

The agent's wallet, 0x9e55…343e on Base, is held by 1Claw. The app asks 1Claw to sign through /v1/agents/{id}/sign; it never holds the key. Signing a login message (personal_sign) is how it signs in to Venice.

1claw pay

To top up its Venice balance, the agent answers Venice's x402 payment request through /pay/prepare and /pay/sign. 1Claw checks the payee and the limits before signing a USDC transfer authorization.

Guardrails

Unattended payments are allowed only to Venice's top-up address, at most $10 per payment and $15 per day. Loosening them needs a human step-up with an authenticator code. Every signature is in the 1Claw audit log.

The money path

  1. The app asks Venice to top up. Venice replies 402 Payment Required with a challenge (minimum top-up $5).
  2. 1Claw /pay/prepare checks the challenge against the allowlist and caps; /pay/sign returns a signed EIP-3009 authorization.
  3. The app sends it to Venice, which settles the USDC on Base and credits the balance.
  4. Generations then spend from that balance. Each request is authenticated with a Sign-In-With-Ethereum message signed by 1Claw (EIP-191, a login that cannot move funds).

Two details found while building it: personal_sign needs the message hex-encoded ("0x" + utf8 hex), and Venice accepts the payment only when re-wrapped as an x402 v2 envelope in the X-402-Payment header. Both are handled in scripts/venice.py.

AssetModel on VeniceCostNotes
KeyframeNano Banana Pro (edit or generate)$0.18Composed from your images and the previous still, so the subject and world stay consistent
Camera moveMiniMax H3 Max, image to video$0.24 at 768p, $0.48 at 1080p5 seconds, starts on one still and is told to end on the next (first and last frame)
  • Never pays twice. Each step is recorded in venice-state.json before it is paid; a re-run resumes and only does what is missing. A redone still makes its neighbouring moves stale, and only those are filmed again.
  • Budget per run. A run stops if it would exceed twice its quote, which leaves room for redos.
  • Join check. After filming, the last frame of each move is compared to the next still (SSIM on a small blurred version). A low score is flagged in the studio.
  • Polling is free. Video jobs are queued and checked every 15 seconds at no cost.

The finished site

A single static page plus three media files. It is built from templates/scroll-site.html with the brief's theme (background, ink, muted, accent and one of four font families).

VisitorWhat plays
Desktop, mouse or trackpadThe film is scrubbed by the scrollbar, with eased inertia. Scrolling up plays it backwards.
Phone or tabletA smaller encode loops on its own; the lines follow its clock. No scrubbing on touch.
Reduced motion or data saverA still poster with all the lines, in normal page flow.
  • Encodes. film.mp4 is 1280×720 and all-intra (every frame is a keyframe), so any scroll position seeks instantly. film-mobile.mp4 is 960×540 with normal compression.
  • Loading. The film only starts downloading when its section is near the viewport.
  • Zip. The site folder with DEPLOY.md for Vercel, Netlify, Cloudflare Pages or any server that serves .mp4 with range requests.

Words and type

On the delivered site, the Words and type panel and the preview stay in sync. Every change saves into the site and the zip.

  • Edit in place. Click any text in the preview and type, or use the fields in the panel. Focusing a line scrolls the preview to where it appears.
  • Style. One per site: Cinema (subtitle-like), Editorial (with a small 01 / 04 index), Gallery (museum wall label), Poster (huge uppercase), Whisper (small lowercase).
  • Per line. Position on a 3×3 grid of the frame, size (S to XL) and entrance (rise, fade, blur, wipe or typewriter).
  • Title position on the same 3×3 grid.
  • Ask the agents. Type a direction ("funnier", "gallery feel", "bigger ending") and press Rewrite words or Lay out text. The typographer explains each placement in one line.
  • Undo steps back to the words and layout before the agents' last change.

The text layer (templates/textlayer.css and .js) is shared: the same code runs in every generated site and in the example on the home page.

Reliability

  • Sessions are saved to outputs/sessions/. Reopening the studio in the same browser picks up exactly where it was, including a render in progress.
  • Renders run detached from the web server and write a log. A server restart or a closed tab does not stop them; the studio replays the log when it reconnects.
  • One render at a time. A second approval waits until the first finishes.
  • Approvals are explicit. Shooting and filming each need a request with approve: true; nothing spends from a page load.

Pricing and payment

A site costs $29 plus $8 per camera move ($53 for three), paid once before anything is generated. It covers the stills, any redos within the run's budget, the film, the words and the site.

  1. Connect a wallet at the storyboard. The studio asks the server whether it is an owner wallet.
  2. Customers pay in USDC on Base, straight to the studio agent's wallet (0x9e55…343e): one ERC-20 transfer from their own wallet. Without a browser wallet, they can send from any wallet and paste the transaction hash.
  3. The server reads the payment from the chain: the receipt must have succeeded, contain a USDC transfer to the studio wallet of at least the price, and be newer than the session. Each transaction is accepted once and recorded in outputs/payments-in.jsonl.
  4. Owner wallets pay nothing. They sign a one-time message (personal_sign, free, moves no funds); the server recovers the signer and checks it against OWNER_WALLETS.
  5. The agent funds its own generation. When an approved render needs more than its Venice balance, it tops up from its wallet through 1claw pay, so customer revenue pays for the work within 1Claw's payee and spending limits.

The AI steps before payment (reading the pitch, the storyboard, rewrites and layouts) are free to try and rate limited per visitor (LLM_LIMIT_PER_HOUR, 40 by default). Signature checks and Keccak-256 are plain Python in scripts/evm.py, tested against eth-account.

Run it locally

  1. Python 3.11+ and ffmpeg on the path. No pip packages are needed.
  2. The studio agent's key in ~/.config/1claw/agents/studio.env (ONECLAW_AGENT_ID, ONECLAW_AGENT_API_KEY), created with scripts/studio-rotate-key.py.
  3. An OpenRouter key in the 1Claw vault at providers/openrouter/api-key, readable by the agent.
  4. Pay guardrails set once with scripts/studio-pay-settings.py (needs your authenticator code), and USDC on Base in the agent's wallet.
  5. python3 app/server.py 8080, then open http://localhost:8080.

The pipeline also runs from the command line: scripts/director.py writes a storyboard, scripts/scrollsite.py configs/name.json prints a quote and --yes renders it.

Deploy on 1Claw

1Claw Cloud Runtimes run a container on Cloud Run with a public URL at {slug}.run.1claw.co. Pro includes one small or medium runtime at no charge. Frameline fits the Python template:

Templatepython (Python 3.12, the 1Claw CLI and sidecar preinstalled)
Presetmedium: 1 vCPU, 2 GB, enough for ffmpeg encodes
AgentBound to the existing studio agent, so the same wallet, guardrails and vault grant apply
SourceA git repository, cloned at start; requirements.txt is installed
Startpython app/server.py, listening on the port the runtime provides
Hostingexpose_http with a slug, set from the dashboard or the API (the CLI has no flag for it)

Prepared in the code

  • ffmpeg. The Python image has none and runs as a non-root user, so apt is not an option. requirements.txt installs imageio-ffmpeg, which ships a static ffmpeg with x264, SSIM and blur; the pipeline uses the system ffmpeg when there is one and that build otherwise. ffprobe is no longer needed.
  • Port and host. The server reads PORT and HOST; on the runtime it runs with HOST=0.0.0.0 on the port the runtime provides.
  • Credentials. The agent key is read from ONECLAW_AGENT_ID and ONECLAW_AGENT_API_KEY (a vault-backed variable on the runtime), then the local key file, then the token the runtime injects.
  • Spend protection. Every paid step needs a verified payment or an owner signature; the AI steps are rate limited. STUDIO_ACCESS_CODE optionally acts as an owner pass for scripts.
  • Showcase. The repository ships the Psyduck film, so the home page works on a fresh container. Private projects, uploads, sessions and payment records stay out of it.

Still to decide or verify

  • Storage. The container's disk is temporary and counts against memory. Films are lost on stop, idle stop or redeploy. For a demo, disable idle stop; for real use, keep runs in object storage or publish delivered sites (for example to IPFS).
  • Background CPU. Renders keep running after the request that started them returns. Whether the runtime gives CPU to background work between requests has to be checked on a first deploy.
  • Token renewal. The injected agent token lasts about two hours. A vault-backed agent key avoids relying on how renewal reaches a long-running process.

Steps

  1. Push the repository to a git host the runtime can clone.
  2. Create a python runtime, medium, bound to the studio agent, from that repository, with the start command HOST=0.0.0.0 python app/server.py, idle timeout 0 and the environment above.
  3. Turn on Expose HTTP with a slug and public inbound auth in the dashboard (the CLI has no flag for it), then open https://{slug}.run.1claw.co.

Known gaps

  • Payment is in USDC on Base only, from a wallet. No cards yet.
  • Shroud no longer routes Anthropic, Google or OpenAI models through OpenRouter (the openrouter/ model prefix is rejected), so the roles use other providers' models.
  • Camera moves can drift from their end still; the join check flags it but does not refilm automatically.
  • Pitch reading and the typographer take 20 seconds to 2 minutes because the model looks at every image.
